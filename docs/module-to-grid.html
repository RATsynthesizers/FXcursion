Part I

The idea

Three things explain most of the design. Everything in Parts II and III follows from them.

01 — the core move

Your Module held four things. Each had a better home.

Your own code was already reaching for this. paramAlloc[] was you pulling parameters out of the objects into one contiguous block, and it was the best structural idea in the C++ design. It survives here — with the Module::allParamNum bump cursor deleted, because with one-of-each-type-per-chain the offset into that block is computable.

03 — the consequence

Two of your constraints removed the allocator

Both of these are yours, from the GUI model. Together they mean memory can be reserved per (plane, effect type) instead of per instance — and once that is true, there is nothing left for an allocator to do.

The one thing that is refused is structural, not resource: a duplicate block type in a chain, a mixer that does not span its column, an effect whose width does not match the chain. Those are configurations the GUI cannot express if it obeys the shared descriptor table — so tripping one is an interface bug, and the running graph is left untouched.

Part II

The machine

What actually runs: the grid, the loop that walks it, the journey of one block of audio, the two execution contexts, and where every byte lives.

04 — the grid

Your screen, and the indices underneath it

The machine is CHAIN_MAX_QTY rows by GRID_SLOT_QTY columns. A cell holds one block: FX, Recorder, Looper, or nothing. One column may instead hold the Mixer, which spans every chain at once. At most one block of each type per chain — so with four slots and four block types, a chain can hold exactly one of each and the grid is exactly saturated.

Your GUI draws IN on the right. aSlot[chain][0] is the IN side. So screen column and array index run in opposite directions, and that is the kind of thing that costs a day.

05 — the engine

One loop, no special cases

Your own description of the grid edges — "first input module processes, then all modules after it, then mixer, then all else" — turned out to be the engine. There is no pre-chain and no post-chain in this design. There is a grid and a mixer column index.

/* grid.c — Grid_Process(). This is the entire engine. */
for (nCol = 0U; nCol < GRID_SLOT_QTY; nCol++)
{
    if ((S8)nCol == pGrid->nMixerCol)
    {
        Mixer_Process(pGrid, apPlane, nFrames);      /* sees every chain at once */
    }
    else
    {
        for (nChain = 0U; nChain < pGrid->nChainQty; nChain++)
            ProcessCell(pGrid, nChain, pGrid->aSlot[nChain][nCol], apChain, nFrames);
    }
}

Why one interrupt is enough. All four SAI blocks are already synchronous to SAI1 block A in your sai.c (SAI_SYNCHRONOUS_EXT_SAI1), so they share one frame sync. That is also why the old saiAdapterCheckUpdate(a1) || saiAdapterCheckUpdate(a2) bug cannot be expressed here: it short-circuited, so whenever adapter 1 had a flag, adapter 2's buffer offset never advanced — while the body went on using the stale offset. With one timebase there is nothing to get out of step.

Part III

The parts

Every block, every parameter, and the reasoning behind each. This is the reference half of the document.

09 — effect types

There are no width-agnostic effects

The rule

Every effect is either mono-only or stereo-only. A mono delay and a stereo delay are two different effect types with two different parameter lists — not one effect with a width flag.

The pool is therefore 22 types, not 11. The GUI still shows 11 entries, because both variants share a display name and the interface resolves which id to send from the chain's width.

This is not bookkeeping. A stereo delay has Ping-pong; a stereo compressor has Link; a stereo tremolo has Phase, and at 180° that same effect is an auto-panner. None of those controls has a mono meaning. The earlier draft had a single Amp with a Pan parameter that silently did nothing on a mono chain — which is exactly the smell this removes.

The consequence you asked for

Because a mono delay is not convertible into a stereo delay, a chain that changes width cannot keep its effects. Validate() enforces it: the effect's declared nWidth must equal the chain's width exactly, or the whole configuration is refused with PROTO_RES_BAD_WIDTH and the running graph is left untouched.

One place I did something different from what you said. You described the chain being cleared on a topology change. I made the audio side refuse a width-mismatched grid instead, because a preset carries a topology and a matching layout — auto-clearing would wipe every preset load. The interface must send a cleared or re-populated chain, which it has to do anyway to redraw the GUI, and it cannot get it wrong because it holds the same descriptor table. The user-visible behaviour is what you asked for; only the question of who does the clearing differs.

Ping-pong, the flagship case

This is the clearest example of a stereo variant being a genuinely different algorithm rather than the mono one run twice.

Every effect, every parameter

What the four stereo-only controls mean:

  • Spread — for the modulation effects, the LFO phase offset between the planes; for the drives, how much harder one side is driven than the other. This is what makes the result wide rather than the same thing twice.
  • Ping-pong — how much of each delay line's regeneration crosses into the other line.
  • Link — how much the two compressor detectors share. Anything below full link makes the image shift with whichever side is louder, so 1.0 is the default.
  • Width — mid/side balance on the Amp; tail decorrelation on the Reverb.
  • Phase — the tremolo LFO offset. At 180° the effect becomes an auto-panner.

11 — FX block

Four slots, and a bypass that keeps the tails

One FX block per chain, up to FXBLOCK_SLOT_QTY effects in it, at most one of each type. The slots run in array order, so reordering is swapping two bytes.

Bypass is "trails on"

A disabled effect is not skipped. Its process function still runs, so its delay line keeps advancing and its tail keeps decaying — then the block's dry signal is restored on top. Stomping a delay off lets the existing repeats ring out instead of freezing them.

/* fxblock.c — the bypass path */
for (p = 0U; p < nWidth; p++)
    memcpy(aDry[p], apChain[p], nFrames * sizeof(FLOAT32));   /* save dry   */

pEntry->pfProcess(&tCtx, apChain, nFrames);                   /* let it run */

for (p = 0U; p < nWidth; p++)
    memcpy(apChain[p], aDry[p], nFrames * sizeof(FLOAT32));   /* restore    */

This is also why toggling an effect never rebuilds the graph: enabling and disabling is one bit in GRID.aFxEnabled, applied on the next block, with no gap. Only adding or removing an effect changes the grid — a menu operation, not a footswitch.

12 — mixer

A routing matrix that occupies a column

Every chain can feed every chain: an n×n matrix of cells, each with a gain and a pan. Input configuration always matches output configuration, so destination chain i has the same width as source chain i — but sources and destinations can still differ in width when a topology mixes stereo and mono chains.

My recommendation, which the switch exists to let you test. Use auto gain to pick the default gain of a newly created connection, and leave it off in normal operation. A bus whose level changes because the user touched a different bus is baffling from the front panel, and with FLOAT32 internally there is no clipping to protect against until the output conversion. Meters plus a clip counter are the honest protection.

13 — looper

Two lengths, four transports

Looper identity is determined by plane, not by chain. Planes 0–1 belong to looper 0, planes 2–3 to looper 1, in every topology. Length is per looper pair; transport is per chain, and the two chains of a pair run independently.

Storage. Four plane buffers of 15 s, packed 24-bit, in SDRAM bank 2 — 8.24 MiB of 16 MiB. Packed 24-bit rather than FLOAT32 because float would cost 11.5 MiB and close the door on undo, which needs a second buffer of the same size.

Length is tempo-derived: bars × Params_BarFrames(). The maximum usable bar count therefore depends on both BPM and time signature, and the GUI needs the same arithmetic to bound its picker. Changing a pair's bar count while either of its transports is non-idle is refused rather than applied — truncating audio playing on the other chain would be worse.

Tempo re-lock is a deliberate placeholder. Each loop records fRecordedBpm and it is written today; playback rate is hardcoded to 1.0. The field exists now specifically so loops and presets saved before re-lock ships stay valid after it does — that is the only expensive part of adding it later.

14 — recorder

A tap that needs no arbitration

The recorder passes audio through unchanged and copies it into the stream sent to the interface over SPI. A chain's recorder occupies the stream slots corresponding to its own planes — and because chain widths always sum to AUDIO_CH_QTY, "a recorder in every chain" needs exactly REC_SLOT_QTY slots in every topology. The map is a pure function of the topology, so it cannot conflict and needs no arbitration.

The stream is fixed width. Four slots are always transmitted, interleaved, with silence in unused ones. Keeping the stride constant means the interface never reprograms its MDMA de-interleave descriptor when the number of taps changes — only if the bit depth changes.

Cross-chip contract. Samples are S32 carrying a 24-bit value, so the interleave stride is REC_SLOT_QTY × 4 bytes. The current Recorder.c on the interface assumes 16-bit samples and an 8-byte stride — that has to change with this. The slot count never changes, only the depth, so it is a one-time edit.

15 — parameters

Addressing, tempo, and the preset blob

A parameter is addressed by (chain, effect type, index). Because at most one instance of each type exists per chain, that address is unique and computable — no allocator, no handle, no negotiation:

g_aFxParam[nChain][eFxType][nIdx]        /* 4 × 22 × 8 × 8 B = 5 632 B, DTCM */

Reordering effects inside an FX block therefore does not disturb their settings, which is what a user expects. Values are always normalised 0..1 on the wire; the mapping to seconds, Hz or dB lives in the effect that owns the parameter, never in the GUI — so adding an effect never requires a change on the interface side.

Tempo

The convention both firmwares must agree on: BPM defines the quarter-note duration, regardless of time signature. Bar length in quarter notes is nBeatsPerBar × (4 / nBeatUnit).

  • 4/4 at 120 BPM → 4 × 1.0 × 0.5 s = 2.00 s
  • 6/8 at 120 BPM → 6 × 0.5 × 0.5 s = 1.50 s (six eighths = three quarters)

A syncable parameter carries bSync and a NOTE_DIV. Resolution happens once per block: FxParam_TimeSec returns the division against the current tempo, clamped to what the effect can actually store — a whole note at 40 BPM is 6 s but the delay line is 4 s, so it clamps rather than reading outside the buffer.

Concurrency

Written by the super-loop, read by the audio ISR, no lock. An aligned FLOAT32 store is atomic on Cortex-M7, so a value is never seen half-written. A parameter update does write three fields non-atomically, so for at most one block — 1.33 ms — the ISR can see a new value with the old division. That is inaudible on a knob and not worth a seqlock.

Presets

The format is fixed now even though save/load is not implemented, because the expensive part of adding it later is discovering that the stored data lacks a field. Magic, version, dimensions, the whole PROTO_CFG, the parameter array, CRC-16. Round-trip tested, including rejection of a single flipped bit.

18 — the C draft

The vtable, specifically

Your AudioController_C draft is where the interesting disagreement is, because the compile errors are not the point — the shape is.

Your module_vtable_t
{
  process,      /* polymorphic  */
  moduleInit,   /* same for all */
  plugNext,     /* same for all */
  plugPrev,     /* same for all */
  unplugNext,   /* same for all */
  unplugPrev    /* same for all */
}

Six entries. Five are the same function for every module type. Those are not virtual functions — they are ordinary functions that happen to take a module_t*.

FX_ENTRY
{
  pfProcess,   /* polymorphic */
  pfReset      /* polymorphic */
}

Two entries, both genuinely per-type. plugNext and friends do not exist because there are no links. Init is a plain call from AudioSys_Init(), because a constructor cannot be virtual — you cannot dispatch through a vtable you have not set yet.

The trap that macro was setting. _MODULE_VTABLE() named plug_next, plug_prev, unplug_next, unplug_prev — and Mixer.c defined its own static functions with those exact names and different signatures. Any use of the macro inside Mixer.c would have bound to the mixer's versions. It compiles, it links, and it silently corrupts the graph. That is the cost of hand-rolling the five things the compiler was doing for you.

19 — provenance

What came from you, unchanged

Worth being explicit about, because the rearrangement can make it look like more was discarded than actually was:

  • The contiguous parameter arena. Pulling parameters out of the objects into one block was the single best structural idea in the C++ design. It is your preset format, your MDMA target and your GUI address space, all for free.
  • The mixer as a routing matrix rather than another node in the chain. Correct instinct; I only moved it into a column.
  • Preallocate everything once, never allocate during audio. Your includeModules() ran once from main and after that FX_ADD only relinked. That discipline is right — I just removed the last allocation too.
  • Hardware adapters separating DSP from HAL. Already plain C, already the right seam. It became the Platform/ boundary that makes the host test build possible.
  • The grid model, and both invariants that make the memory design work. Widths summing to 4 and one-of-each-type-per-chain are yours. They are the reason there is no allocator.
  • Your description of the grid edges — "then mixer, then all else" — which turned out to be the engine, and is simpler than the pre/post-chain structure I had carried for three rounds.
  • The mono/stereo split itself. You were right that a stereo delay is a different effect, not a wider one. It cost 11 extra ids and zero extra memory, and it deleted a whole category of "this parameter does nothing right now".
  • Two bugs you found by asking questions: loop transports surviving a plane remap, and the absence of any declared width behaviour at all.

Part V

Practical

How to extend it, what has to happen before it runs on hardware, and what is still undecided.

20 — extending

Adding an effect

  1. Decide the two variants first. Before writing any DSP, answer: what does the stereo variant have that the mono one cannot? If the honest answer is "nothing, it just runs twice", write only the mono one.
  2. Copy fx_template.c / .h, rename FxTemplate_* to FxMyEffectM_* and FxMyEffectS_*.
  3. In Shared/fx_defs.h: append FX_MYEFFECT_M and FX_MYEFFECT_S in that order, mono at an even id (FX_VARIANT_FOR_WIDTH depends on it), without renumbering anything; bump FX_TYPE_QTY by two; add both parameter index enums.
  4. In Shared/fx_defs.c: both descriptor arrays and both rows, with nWidth 1 and 2 and the same display name.
  5. Copy both fx_defs files to the interface project. They are duplicated on purpose and must stay byte-identical.
  6. Modules/params.c: two rows in aDefaultNorm.
  7. Modules/Effects/fx_registry.c: two rows.
  8. If it needs a delay line, declare one static array indexed by plane and let both variants share it — see fx_delay.c. Add its size to the budget in mem_map.h so the static assertion keeps covering the real footprint.
  9. Add a test.

The five rules inside a process function

  1. Process in place. apPlane[p] holds the input on entry and must hold the output on exit.
  2. State is indexed by plane, parameters by chain. There is no instance object and nothing is allocated.
  3. Know your width at compile time. A mono effect touches apPlane[0]; a stereo effect touches both. The grid guarantees the chain matches, so there is no runtime width branch.
  4. Resolve parameters once per block, not per sample — that is most of why block processing is fast.
  5. Smooth anything the user can turn that multiplies the signal.

And one prohibition: no HAL, no malloc, no printf, no float literal without an f.

21 — bring-up

Before this runs on hardware

  1. Linker script. .dtcm and .itcm are (NOLOAD) with no input-section patterns in STM32H743VITX_FLASH.ld, so objects land there only via GNU ld's orphan-merge-by-name rule and get neither the .data copy nor the .bss zero fill. Every static here is garbage until AudioSys_Init() runs — which is exactly why that function exists and initialises everything explicitly. In the old C++ project this was hidden by global constructors, and it is the single most likely way a C++→C port fails mysteriously. .itcm needs AT> FLASH plus a copy loop in Reset_Handler before any code goes there. Add .sdram_fx and .sdram_loop output sections for the two banks.
  2. FPSCR.FZ at boot. One line. Reverb and delay tails decay into denormal range, and denormals can cost 10–100× — a CPU spike that only appears when the room goes quiet.
  3. MPU. Keep RAM_D1_DMA non-cacheable. Map both SDRAM banks write-through, no write-allocate: delay lines are streamed with no reuse, so write-allocate only buys a read-for-ownership on data that is never read back.
  4. SAI. All four blocks are already synchronous to SAI1 block A, so one interrupt drives everything and SAI2's callbacks stay unused. Move to SAI_PROTOCOL_DATASIZE_24BIT with word-width DMA.
  5. Build flags. -O2 or -O3 on the DSP files, not -Os. -Wdouble-promotion is not optional.
  6. Interface side. Recorder.c de-interleaves assuming 16-bit samples on an 8-byte stride; the stream here is S32 carrying 24 bits, so the stride is REC_SLOT_QTY × 4. Copy fx_defs.*, fx_protocol.h and fx_crc.* across in the same commit.
  7. SDRAM timing. CAS 2 at 120 MHz is aggressive for a W9812G6JH. It evidently works on the interface board, but the audio board has different trace lengths, and SDRAM marginality shows up as rare bit errors in delay tails — faint crackles, miserable to diagnose. Run a memory test at temperature before trusting it.

23 — the code

File map and reading order

Six files, in this order

Rather than 7 800 lines, read these and you have the whole design:

  1. Modules/Effects/fx_common.h — the contract. One page. Everything else obeys it.
  2. Shared/fx_defs.h — the pool, the widths, the shared dimensions.
  3. Modules/grid.h — the model, the invariants, how a config change is applied.
  4. Modules/grid.c, Grid_Process() at the bottom — the engine, 30 lines.
  5. Config/mem_map.h — why there is no allocator, with the arithmetic.
  6. Modules/Effects/fx_delay.c — one real effect, both variants, using every part of the design.

Then Shared/fx_protocol.h when you start on the interface side, because that file is the contract between the two chips.

Everything here describes AudioController/AudioController_Claude as it stands. The DSP layer builds and runs on a PC — 89 268 checks, 0 failures, 0 warnings at -Wall -Wextra -Wdouble-promotion -Wfloat-conversion -Wshadow -Wcast-align. Platform/audio_io.c is the one file that has never been compiled, because it is the only one that talks to the HAL.
