FXcursion · interface ↔ audio · SPI1

One Wire,
Two Streams

The recorder and the looper share a single SPI link with no length, no CRC, and no way to tell one slot from another except by counting. Everything that looks over-engineered in this code exists because of that one fact — including the one slot per frame now spent making it safe. Here is the whole protocol, and an honest list of what could be simpler.

The code looks bloated in places, and some of it was. Seven findings are marked below; four have been fixed — including one that was corrupting three quarters of every recording during a loop save, and one that would have stopped the link ten milliseconds after boot — and the rest are judgement calls left in place with the reasoning recorded. Most of the remaining bulk is one constraint pushing outward, and it is worth seeing that constraint clearly before deciding what to cut.

01The constraint everything follows from

SPI1 carries a continuous, positionally framed stream. The audio board sends one frame per audio block, forever. The interface knows which sample belongs to which channel purely by counting — a slot is channel 2's because it is the fourth word to arrive, not because anything in it says so.

There is no length to validate and no CRC to fail. That makes it fast, and it makes it fragile in exactly one way:

Lose a single 32-bit word and every slot is permanently rotated.
The stream keeps flowing. The data keeps looking like audio.
Every channel is in the wrong file from that moment on.

That is not a hypothetical. It is why four things in this design that each look like overkill are not:

  • The receive DMA is armed once and never re-armed — the gap between two transfers is precisely where a word goes missing.
  • The interface arms its routing before the audio board is told to start, and the audio board is told to stop before the routing is torn down.
  • Loop data cannot have its own SPI transaction, because starting one would mean re-arming. It has to ride inside the recorder's frames.
  • The frame width is fixed and never negotiated, because changing it mid-stream needs both ends to switch on the same frame — and that is the rotation above, deliberately invited, twice per loop.

One thing has changed since that paragraph was first written. The stream now carries a sync slot — one word per frame that the receiver can predict. A rotation is still just as destructive, but it is no longer invisible: it is caught within one frame, counted, localised to a word offset, and the affected audio is replaced with silence rather than with someone else's channel. Everything above still holds. What follows from it is now a fault you can see.

One SYNC slot, FX_FRAME_REC_SLOT_QTY recorder slots, and FX_FRAME_LOOP_SLOT_QTY loop slots. Thirty-two slots, always. The frame does not change size, ever.

The width used to be negotiated — four slots when idle, wider for the life of a loop transfer, narrow again afterwards. That is gone, and its removal is the single biggest safety change in this design. A mid-stream width change requires both ends to switch on precisely the same frame boundary; disagree by one frame and every slot is rotated permanently, with nothing in the stream able to reveal it. That switch happened on every loop save and every loop load — at the busiest moment the link ever has. Now it never happens.

The price is 27 slots of zeros on an idle link: 5.2 Mbit/s of the 96 available, spent to delete a failure mode. A fixed width also makes the receiver's geometry a compile-time constant — 128 frames per half, not a division by a number that arrived in a handshake.

Thirty-two, and not any number you like. The receiver's ring is a fixed count of words and its half-transfer interrupt fires at the halfway word, so the width has to divide that half exactly — otherwise the boundary lands mid-frame and everything after it is rotated. At 4096 words per half the divisors are 8, 16 and 32. Thirty-two is the widest, which makes the loop as fast as the wire allows.

The three parts of the frame are read completely differently, and that difference explains most of the code:

The MDMA-routes row is load-bearing. The MDMA offers five routes — one channel plus four linked-list nodes. Four are spoken for by the recorder planes, which leaves exactly one. Twenty-seven loop slots as twenty-seven routes would not have fitted; as one contiguous run, it does. That is why the loop slots are grouped at the end of the frame rather than interleaved among the recorder's. And the sync slot costs no route at all, because the CPU reads it directly and the MDMA simply steps over it.

02bThe sync slot

One slot in thirty-two, spent buying the difference between a fault you can see and a fault you cannot.

Section 01 is about a stream with no framing: lose one word and every slot is rotated forever, silently, with plausible audio in every channel. The sync slot is the answer to it. It carries a value the receiver knows in advance, so a rotation stops being invisible.

    31              16 15               0
    +-----------------+-----------------+
    |   MARK 0xFB5A   |   SEQ 0..65535  |
    +-----------------+-----------------+
       constant           per-frame, wrapping

The mark catches rotation. 0xFB5A is not arbitrary. Its top byte is neither 0x00 nor 0xFF, which is what a sign-extended 24-bit sample's top byte always is — so ordinary audio arriving in the wrong place can never forge it. It is also not 0x0000, 0xFFFF, 0x5555 or 0xAAAA, so a dead bus, a stuck line or a clock-like pattern cannot either.

The sequence number catches loss, which is a completely different fault with a completely different cause. Together they separate the two:

What the receiver concludes
ObservedDiagnosisReported as
mark right, seq = expectedthe stream is where it should benothing — the half is de-interleaved normally
mark wrongrotated or corrupt. The scan then searches the frame for where the mark actually is; that offset is the rotation.recSyncMarkFaults, recSyncLastPhase
mark right, seq jumpedframes lost, alignment intact. The jump size is how many.recSyncSeqFaults, recSyncLastGap

A phase of 1 means a single word slipped. A large phase, or FX_FRAME_PHASE_NONE, means the data is corrupt rather than merely misaligned — a different thing to go and investigate. That distinction is the whole reason the sequence number shares the slot with the mark instead of the mark using all 32 bits.

It costs nothing in strength, either. A random word at the frame boundary has to match both the 16-bit mark and the exact expected sequence number: 2⁻³² per frame, one false accept per 25 hours at 48 kHz — and the very next frame catches it anyway.

What happens to a bad half

FxFrame_Scan reads slot 0 of all 128 frames — one load and one compare each, 128 words out of 4096 — and if any frame fails, the receiver discards the whole half and writes silence, then stops predicting and re-adopts whatever sequence number arrives next.

All-or-nothing per half, on purpose. A slipped word rotates the stream permanently, so a half with one bad frame has every later frame bad too — and so does the next half, and every one after it. Salvaging the good prefix would rescue at most 2.7 ms, once, in exchange for a partial MDMA and a second write path into the same chunk.

And the ring still advances. That is not incidental — it is why the silence is written rather than the half simply skipped. A discarded half has to leave a hole of the right length, or the recording runs fast and every take after the fault is shorter than the performance was. A gap that keeps time is a fault a musician can point at; audio that drifts is one nobody can.

04What each piece is for

You said you don't know why loop_xfer has the functions it has, or what a "spool" is. Here is every module on the path, and the one job it exists to do.

Audio controller — the sender

Two of these are worth separating, because they are the ones people conflate. Widening the frame speeds up the RAM-to-RAM crossing and nothing else. The recorder's own rates do not move with it at all:

note the card figure is not measured

Every number above is derived from constants in the source. The loop-to-card time is not — it is bounded by whatever the SD card sustains, and nobody has timed an f_write on the actual hardware yet. Treat any end-to-end "saving takes N seconds" claim as unmeasured until that happens.

The burst must finish inside the block, or the next block has nowhere to go and is dropped — silently, in both the recording and the loop. That is the entire reason for 96 MHz rather than 48:

frame width          48 MHz    96 MHz   share of the 1333 µs block
 8  1+4+3 loop          26%       13%     divides the half
16  1+4+11 loop         51%       26%     divides the half
32  1+4+27 loop        102%       51%     divides — IN USE, and 48 MHz cannot fit it

This table is why the link runs at 96 MHz. The chosen frame does not fit in a block at 48 MHz at all — 102% of the budget — so the clock is not headroom for its own sake, it is what makes a 32-slot frame possible. At 96 MHz the same frame leaves half of every block free, and it is a constant half rather than a figure that jumps when a transfer starts.

51% sustained would have been a cliff back when it only happened during a transfer, coinciding with the DSP at full tilt and both SDRAM banks serving a looper alongside delay or reverb. Fixed, it is simply the operating point: nothing changes when a loop starts, so there is no transient to survive.

Notice the width column is not a free choice: only 8, 16 and 32 appear because those are the widths that divide the receiver's 4096-word half. 20 and 24 are missing because they do not, and a frame that does not divide puts the half-transfer interrupt in the middle of a frame. An earlier version of this design shipped with 20.

06Saving a loop, in order

Nine steps. The ordering constraints are the interesting part — three of them are not negotiable.

GUI        LoopSession_StartSave(looper, planes, name)
             │
  1          ├─ LoopSpool_Acquire()          take slot A or B, or refuse
  2          ├─ Recorder_ArmLoopDest()       ← ARM BEFORE ASKING
  3          └─ LOOP_OPEN ────────────────────────────────────▶ UART
                                                     │
  4                          LoopXfer_OnOpen()  ◀─┘  how long is the take?
  5          ◀──────────────────────────────── LOOP_STAT(READY, bytes, slots)
             │
  6          ├─ FxLoop_OpenReply()           both sides now agree on the size
  7          └─ LOOP_CTL(START) ──────────────────────────────▶
                                                     │
  8                    loop slots stop carrying zeros; blocks flow
             ◀════════════ MOSI, 27 loop slots per frame ═════════
             │
  9          ◀──────────────────────────────── LOOP_STAT(COMPLETE, crc)
             │
             └─ LoopSession_Poll()
                 ├─ wait for both: bytes landed AND peer reported
                 ├─ Crc32_Ieee(staging) == peer crc ?
                 ├─ Recorder_DisarmLoopDest()
                 └─ LoopSpool_Commit()  → queued for the card

The three orderings that matter

Arm before asking (step 2). The route is in place before any possibility of a block. A block arriving with nothing routed is not recoverable — there is no framing to notice it with, and the loop would simply be missing bytes from its middle.

Stop sending before disarming (step 9). The reverse. The frame no longer narrows — the loop slots stay on the wire carrying zeros — but the route still has to go away in the right order, because while it is armed it faithfully writes those zeros into the staging buffer past the end of the take. The audio board stops filling first, then the interface stops routing.

Wait for both conditions. The interface knows its byte count is satisfied; the audio board knows it sent everything. Waiting on the local count alone would run the CRC comparison against a value that had not arrived yet. Waiting on the report alone would checksum a staging slot the MDMA had not finished filling.

R1 could be simpler

Two modules where one might do

LoopSpool and LoopSession are separate because one owns the card and the other owns the wire. That is a real seam — the spool's queue and recorder-priority logic have nothing to do with the protocol — but it costs two headers, two init calls and a shared nSlot that both touch.

If you merge them, you lose the ability to test the card side without a link, which is currently possible. I would keep the split, but the criticism is fair and the cost is real. If it stays, nSlot ownership should move entirely into the spool with the session asking for it by handle.

07The card, and who gets it

The recorder writes four WAVs continuously. A loop save wants the same card. A card handles one sequential stream far better than two interleaved, so they take turns — and the turn order is deliberately not first-come.

loop A writes  ──────────────▶ done
                                 │
recorder waits, ring filling ────┤  backlog: ~3 MB of a 50 MB ring
                                 ▼
                          RECORDER GOES NEXT   even though loop B is queued
                                 │
                        catches up at ~4× real time
                                 │
                                 ▼
loop B starts immediately  ────────────────────▶

LoopSpool_IsBusy() stays TRUE across all of it.
It never blinks false in the gaps.

The recorder goes next because it has been locked out for seconds and is carrying a backlog. Putting a second loop ahead of it is how a backlog becomes an overrun, and overrun audio is gone. The loop is already safely in SDRAM; the recorder's backlog is not.

The busy flag staying true is what makes the "saving" indicator honest, and it is also the gate: LoopSpool_Load returns RESULT_BUSY during that whole window rather than queueing, because a read starting mid-recovery locks the recorder out a second time before it has cleared the first.

R2 worth measuring

The CRC and the packing both sit in the audio block

Per block, with a transfer running, the audio side spends roughly 2.6–5% of its budget on the CRC over 4096 loop bytes, plus the window copies. That is affordable. It is listed because it is invisible — nothing reports it, and it only appears when a loop transfer coincides with a heavy patch.

Worth doing: put the block's worst-case cycle count on the debug UART. You already have DWT->CYCCNT sampled in ProcessHalf.

08Review findings

Eight things. R3, R4, R6 and R7 are fixed — kept here rather than deleted, because a fix with no record of what it fixed is how the same mistake gets made twice. R8 is open and needs hardware. The rest are judgement calls where the current shape is defensible but the cost is real.

R6 and R7 are the two worth reading if you read only two. Both were live in committed code, both were silent, and both were found by writing this document rather than by testing. R7 is also worth reading as a caution: its first fix was wrong in the other direction, and applying a correct argument to both boards by symmetry is exactly how that happened.

R7 defect · fixed · would have blocked bring-up

The two ends need opposite DMA modes, and the reason is not symmetric

Circular mode on this link is not about the buffer wrapping. From the HAL:

stm32h7xx_hal_spi.c — "Set the number of data at current transfer"

if (hspi->hdmatx->Init.Mode == DMA_CIRCULAR)
    MODIFY_REG(..., SPI_CR2_TSIZE, 0);      endless
else
    MODIFY_REG(..., SPI_CR2_TSIZE, Size);   stops after Size

With TSIZE set, the peripheral raises EOT and suspends after that many frames. The link would have stopped after 8192 words — about 10 ms — and the already-circular receive ring would never once have wrapped. Everything downstream keeps counting slots as though the stream were still running.

Worse, the HAL reads the mode off the TX channel even in the TransmitReceive path. The interface's TX being DMA_NORMAL gated the whole link on its own, regardless of its RX already being correct.

Interface TX was also HALFWORD on both sides of the transfer while SPI1 is SPI_DATASIZE_32BIT and the buffer is int32_t. RX had been corrected to WORD in a hand-added USER CODE block; TX never was.

The correction, which went the wrong way first. The reasoning above is sound for the slave and was then applied to both boards by symmetry — all four channels circular. That is wrong for the master, and would have wedged it on its first block.

The master does not stream. It only ever calls SPI_TP_SendFrame or SPI_TP_SendRecvFrame — finite bursts of 2048 words, one per audio block — and it relies on TxCplt / TxRxCplt firing to clear bTxBusy. With circular TX and therefore TSIZE = 0, that burst never ends, the callback never fires, bTxBusy latches, and every later block is refused as RESULT_BUSY while the peripheral keeps clocking.

So the modes are opposite by design, not by oversight, and neither board's setting should be propagated to the other:

audio  (master)   DMA_NORMAL     TSIZE = Size   finite burst per block, EOT is "frame done"
iface  (slave)    DMA_CIRCULAR   TSIZE = 0      one endless transfer, armed once, never re-armed

All four channels are WORD. Everything is fixed in the .ioc as well as the generated source — the .ioc being the part that matters, since the RX fix lived only in a USER CODE block that CubeMX drops on regeneration.

Note what the burst size buys: 2048 words is 64 frames exactly, and a half-ring is 4096 words is 128 frames. So a burst is always a whole number of frames and a half is always two bursts. A dropped burst therefore costs 64 frames and leaves alignment intact — and the sequence counter reports the gap as exactly 64. Frame loss and rotation stay distinguishable even when the master skips a block.

R8 open · needs an oscilloscope · could rotate the stream

NSS deasserts between bursts, and the slave is inside one endless transfer

This falls straight out of R7. The master drives SPI_NSS_HARD_OUTPUT, so its peripheral asserts NSS when a burst begins and releases it at EOT — low, high, low, high, once per burst, every 1.33 ms. The slave is SPI_NSS_HARD_INPUT and believes it is inside a single transfer that runs for the life of the device.

The question. When the slave's NSS input goes high between bursts, does it (a) pause and resume cleanly on the next burst, or (b) treat it as end-of-transfer and tear down, error, or reset its internal word counter?

If (b), the endless transfer either dies after the first burst or resynchronises its counter so each burst lands at a different phase — a permanent silent rotation, which is the failure this entire frame design exists to catch. It would be caught. You would simply have a link that reports faults continuously and records nothing.

What to discount. An earlier review flagged SPI_NSS_PULSE_ENABLE on the master — NSS pulsing between every individual word — as the danger. That should not fire: CFG2.SSOM only interleaves those pulses when MIDI > 1, and MasterInterDataIdleness is 00CYCLE here. Right instinct, wrong mechanism. The exposure is between bursts, not between words.

How to settle it. Two probes on the interface's SPI1 pins — NSS (driven from the audio side's PG10) and SCK — triggered on NSS rising. Does NSS actually go high between bursts, how long is the gap, and does SCK stop cleanly. The half that needs no scope: run the link and watch FxFrame_Scan. A non-zero phase reported at roughly the burst rate is the answer.

If it is (b). Restructuring the master to arm once and fill halves — the way the slave already works — holds NSS low permanently and deletes the question. It is a larger change than it sounds, because RecSpi_PushBlock, RecStream_Stage and the bTxBusy handshake are all built around finite bursts, but it is the structurally cleaner arrangement for a positionally framed stream.

R6 defect · fixed · was corrupting recordings

The chunk pointer advanced by a full chunk no matter how much data arrived

REC_CHUNK_SAMPLES was pinned to 1024 — frames-per-half at the narrow width — while the de-interleave wrote 4096/w frames and the callback advanced the ring by a whole chunk regardless:

              arrives    written    ring advances
 at  4 slots    1024       1024        1024   OK
 at 16 slots     256        256        1024   wrong

every chunk = 256 fresh samples
            + 768 samples of audio from one lap earlier
and the file advances 4× faster than real time

Live at the committed 16-slot width, during any loop transfer. Three quarters of the recording was stale audio from 5.5 seconds prior, and the take ran fast — with nothing reporting either.

What changed. The fixed frame makes REC_CHUNK_SAMPLES a compile-time constant equal to frames-per-half (128), so the two cannot disagree. REC_CHUNKS went 256 → 2048 and REC_WRITE_CHUNKS 16 → 128 to hold the 5.46 s absorption and the 341 ms write batch across the eight-times-smaller chunk. The ring is the same 4 MiB. A static assert now pins the absorption at ≥ 5 s, because the two constants that set it move independently.

R3 defect · fixed

The receive ring was sized for a four-slot frame only

The ring is REC_RX_WORDS = 8192 words, and the de-interleave was told REC_RX_HALF_FRAMES = 1024 frames unconditionally. Correct at four slots per frame, wrong at every other width:

half = 4096 words

 at  4 slots/frame  →  1024.0 frames   OK
 at 20 slots/frame  →   204.8 frames   not even a whole number

it would have read 1024 × 20 × 4 = 81,920 B
from a half that holds 16,384 B

A five-times overrun into whatever follows the ring, the first time a loop was saved. LoopSession_FillTx's half offset had the same bug.

First fix made frames-per-half a function of the ACKed width, required that width to divide the half, and refused an illegal one rather than clamping. That was correct but left the width variable, which is what R6 then tripped over.

Final fix: the frame is fixed at 32, so frames-per-half is simply a constant:

REC_RX_HALF_WORDS     (REC_RX_WORDS / 2)          4096
REC_FRAMES_PER_HALF   (REC_RX_HALF_WORDS / 32)    128

REC_WIDTH_IS_LEGAL and the run-time refusal are gone — with nothing negotiating a width there is nothing to validate, and the divisibility is a static assert. The whole class of bug moved from run time to build time.

R4 real cost · fixed

LoopXfer_At() did two divisions per payload byte

It converted a byte offset into a plane index and an offset within that plane, with a / and a %, once per byte:

4096 payload bytes per block  →  8192 divisions per block

at ~10 cycles each  =  81,920 cycles
block budget        = 639,840 cycles      ≈ 13%

Thirteen percent of the audio block spent on address arithmetic, for a pointer that almost always just advances by one. The plane boundary is crossed once in a multi-megabyte loop.

What changed. A walking pointer: pWalk and nWalkRemain, both advanced by one per byte, with the plane step taken only when the countdown reaches zero. The divide-and-modulo now happens once per block to re-derive the pointer from nByteOfs — which also means a session reset between blocks cannot leave a stale pointer behind.

divisions per block   8192  →  2

LoopXfer_At survives for the CRC span, where it runs at most twice per block.

R5 now worth doing · the objection to it has gone

The routes are rebuilt from scratch every half

MDMA_Trigger_Deinterleave recomputes all five routes and runs FxInterleave_Xfer's full validation on each, now every 2.67 ms rather than every 1333 µs.

The previous verdict here was "leave it", and the reason was that caching needs invalidation, and the thing that would invalidate it — a width change — is exactly the moment you least want a stale descriptor. Width changes no longer exist. Four of the five routes are now genuinely constant for the life of the link: same slots, same widths, same frame count. Only the destination offsets move, by one chunk each time, and only the loop route appears and disappears.

What to do: build the four recorder routes once at init and patch only CDAR per half. The validation still runs at init, where it belongs. This is no longer a trade against safety — the fixed frame removed the hazard that made caching risky — so it is simply a saving now.

Also new, and cheap: the sync scan adds 128 uncached word reads per half. RAM_D2 is non-cacheable, so roughly 2–3 k cycles at 2.67 ms intervals — about 0.2% of one core. Worth knowing about, not worth avoiding: it is what buys R7's whole class of fault becoming visible.

R6 smell · justified, but flag it

RecStream_StageSlots() hands out a writable pointer

RecStream_Buffer returns const because nothing outside that module should write a staged block. StageSlots exists to break exactly that rule, so the loop transport can fill its slots in place.

The alternative is a second 5 KiB buffer and a copy per block. That is worse. But the const-breaking function is a genuine smell and should stay narrow: it is valid only for the half Stage just returned, and only before the transport starts. Nothing enforces that today.

Cheap hardening: have Stage return the writable pointer directly instead of an index, so there is no window in which a stale index can be passed.

R7 not bloat — keep

Things that look redundant and are not

Two staging halves on the audio side. One in flight, one filling. With one, a block would be written into the buffer the DMA is reading.

The DTCM window in loop_mem. Looks like a leftover from the PSRAM design. It is not: it handles the loop wrap in one place, and DTCM is zero-wait where SDRAM costs a row activate per sample.

Zeroing the loop slots when no transfer runs. Without it a finished transfer's last block stays in the staging buffer and the next frame carries stale audio in slots the interface is still routing.

Two CRCs. They are over different memories — the sender's looper and the receiver's staging. Comparing them is the only check on a link that carries no CRC of its own.

09The interface's looper API

Everything the GUI needs already exists and is callable. What does not exist is anything calling it. This chapter is the list of functions a TouchGFX screen binds to, and the two calls whose absence currently makes the whole transport inert.

What still has to be written here

The STREAM call. Put it in the CtrlLink task on the dead→alive edge, beside the existing pushConfig, not in RecorderInit — otherwise an audio-board reboot comes up with streaming off and nothing ever turns it back on. Gate it on tLastAck.nStreamWidth == FX_FRAME_SLOT_QTY so two boards built from different commits refuse each other instead of streaming a rotated frame.

A command queue between the GUI and CtrlLink. LoopSession_StartLoad blocks on the card, so it must never be called from tick() or the TouchGFX task — that stalls the display for as long as the read takes. The screen posts an intent; the CtrlLink task performs it.

Telemetry into the widgets. aTransport[], aLoopPos[] and aLoopLen[] arrive over the UART link but nothing surfaces them to a screen, so a progress bar has nothing to read.

gap there is no abort

Nothing sends LOOP_ACT_ABORT. A user who starts a save cannot cancel it; they wait for the stall watchdog (3 s without progress) or for the transfer to finish. Add LoopSession_Abort() before shipping a cancel button, not after.

10The audio side: commands in, buffers underneath

The audio board never initiates a transfer. It answers. Its whole role is: accept an OPEN, agree or refuse the geometry, then move 27 slots per frame between the wire and SDRAM until the byte count is met — and report what it thinks happened.

Where the bytes actually live

Two banks, one looper each, so a save out of one never contends with playback from the other:

SDRAM bank 1  .sdram_loop_a   looper 0, planes 0-1   take + undo   11 MiB
SDRAM bank 2  .sdram_loop_b   looper 1, planes 2-3   take + undo   11 MiB

  one plane-copy   2 880 000 B   = 20 s x 48000 x 3 B
  stereo take      5 760 000 B   = the payload that crosses the wire
  undo copy        never crosses - it is local history

A SAVE walks LOOP_COPY_TAKE of both planes as one contiguous byte run; a LOAD writes the same run back. The undo copy is never transmitted, which is why an 11 MiB region holds a 5.49 MiB transfer.

What still has to be written here

Nothing validates a loaded take. LoopXfer_Block lands the bytes in SDRAM and the CRC confirms they arrived intact — but no code then tells the looper that plane now holds 20 seconds of audio and is playable. After a LOAD completes, something must set the take's length and mark the plane valid, or the user loads a loop and hears nothing.

Undo is storage-only. LoopMem_Snapshot works and is tested; no command reaches it.

note the transport is symmetric, the wiring is not

Both directions are implemented in LoopXfer_Block and both are exercised by the host suite. The asymmetry is above it: a SAVE ends with bytes on a card, which is a complete story, while a LOAD ends with bytes in SDRAM that nothing has been told about. That is the single largest piece of unwritten code on this side.
